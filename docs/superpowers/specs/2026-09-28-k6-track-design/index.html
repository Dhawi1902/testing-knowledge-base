k6 Track — Design Spec

Date: 2026-09-28 Status: Approved in brainstorming, awaiting implementation plan Scope: Basics + Applying Load (option 1). Advanced topics go to a 99-future page.

1. Purpose​

A k6 track in the same style as the JMeter and Playwright tracks. It teaches a tester to script, load and report a k6 test end to end, using the Pizza Playground as the target.

It builds on the Performance Testing module:

  • performance-testing/01-fundamentals defines the six test types.
  • performance-testing/03-mapping-to-k6 shows the one-script, -e PROFILE=... idea.

The k6 track goes deeper: every k6 setting needed to run each test type, plus auth, correlation, test data, checks, thresholds, debugging and reporting.

Success looks like

  • A reader with Docker and k6 installed can clone this repo, start the playground, and run every sample script.
  • Every code block on a doc page is taken from a file in k6/sample/ that was run against the playground.
  • Each of the six test types has a run command that works with the sample.

Non-goals for this version: Grafana/InfluxDB live monitoring, distributed runs (k6-operator), CI pipelines, the k6 browser module, k6 Cloud, TypeScript. All of them are listed in 99-future-to-explore.

2. Decisions​

  • k6 version: v2.2.0 (installed locally). Stated on the index page.
  • Language: plain JavaScript (ES modules), as k6 runs it. No bundler, no npm.
  • Target: Pizza Playground running locally via docker compose up. BASE_URL defaults to http://127.0.0.1:8080 (IPv4 to avoid the localhost quirk).
  • Sample location: k6/sample/ in this repo, next to the docs that quote it (same as playwright/sample/).
  • No mirror copy of docs in k6/docs/. The Docusaurus pages under docs/k6/ are the only copy.
  • Existing mapping page stays. performance-testing/03-mapping-to-k6 is unchanged; page 08 links to it and goes deeper.

3. Sample project​

k6/
├── PLAN.md               Progress table and next steps (like playwright/PLAN.md)
├── README.md             How to run the sample
└── sample/
    ├── lib/config.js     BASE_URL, load profiles for the six test types
    ├── lib/auth.js       login(email, password) -> token, authHeaders(token), resetPlayground()
    ├── data/customers.csv  Copied from pizza-playground/test-data/
    ├── 01-first-test.js  GET /menu, one check
    ├── 02-auth.js        Shared token from setup() vs one customer login per VU
    ├── 03-order-flow.js  Login -> menu -> create order -> poll payment status
    ├── 04-thresholds.js  Order flow with groups, tags, per-endpoint thresholds, custom metrics
    └── 05-load-model.js  Order flow under any profile or executor, chosen with -e

Behaviour shared by scripts 02–05

  • setup() logs in as owner@playground.local and calls POST /api/v1/admin/reset, so each run starts at order 1001.
  • Customers come from customers.csv through SharedArray. Each VU uses the row matching its VU number, wrapping around the 20 customers.
  • Orders are created with autoPay: true by default. -e AUTOPAY=false sends orders through the mock gateway instead, and -e MOCK_DELAY=<ms> adds the X-Mock-Delay header.
  • Scripts fail fast with a clear message if the playground is not reachable (the check in setup()).

Auth patterns taught (page 05, script 02)

  1. Shared token: one login in setup(), returned as data and used by every VU. Fits admin endpoints; the JWT lasts 12 hours.
  2. Per-VU login: each VU logs in as its own customer on its first iteration and keeps the token in a module-level variable. Fits /orders/mine, where the user matters.

6. Validation​

  • Every script is run against a local playground while writing. npm run build must pass.
  • Long profiles (stress, endurance, spike) are checked with k6 inspect and a short run with the durations scaled down. The status table says "Validated (scaled)" for those rows rather than claiming a full 4-hour run.
  • Screenshots (web dashboard, HTML report) go under docs/k6/images/, or stay as <!-- TODO: Screenshot - ... --> where not captured.
  • Status table columns: Page | Written | Validated | Screenshots.
